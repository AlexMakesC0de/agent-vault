# Architecture and recovery

Schema 2 separates a private central profile from project vaults. The local user router selects one profile using `~/.config/agent-memory/config.json` and projects using `projects.json`. These are device configuration, not synced memory.

The profile's canonical `SOUL.md` is authored Markdown shared by every agent (1,500 characters; an existing file up to the former 2,200 still loads with a warning until `set-soul` shortens it). `.agent-vault-profile.json` records preference/general entries, evidence, expected revisions, history and imports. `USER.md` (2,000 characters) and general `MEMORY.md` (2,200) are projections. The three central limits together stay near their former total because central context and a project's core share one 9,500-character hook message; preferences get the room an authored identity rarely needs. Each project owns `docs/knowledge/memory/state.json` (scope project) and its `MEMORY.md` projection (2,200). Formatting counts against limits. Capacity errors refuse the change without truncation. At 85% of a limit, context, `status` and the result of each update carry one "Near the cap" line, so consolidation happens before a save fails. Central detail too long for a core goes in notes linked from the profile's `notes/README.md`, which context points to when it exists; the core keeps a one-line pointer.

Schema 1 remains readable for migration. Its generated project SOUL was a legacy design, superseded by central identity. New setup never creates it.

## Concurrency and recovery

Writes use local platform locks, atomic file replacement and revision checks. POSIX uses flock; native Windows uses msvcrt. State is written before derived USER/MEMORY files; interrupted projection writes are repaired with `render`. Preserve unexpectedly edited projections before rendering: they may contain manual information not in state. SOUL is read directly and render never rewrites it. `set-soul` records before/after history before writing canonical identity; if interrupted, inspect that record and reconcile the canonical file explicitly.

Profile initialization refuses partial/existing files rather than resetting them. Restore from Git/backups or import deliberately. No auto-empty fallback is used for a missing configured profile.

Migration locks profile before project, previews classification/capacity, archives exact source bytes with hashes, commits destination first, then project state, and finally removes verified legacy SOUL. The journal tracks phases and immutable preimages; retry the same command with `--apply` to finish an interrupted migration. Preview is read-only apart from lock files. Unexpected edits, import collisions or damaged archives are refused. Original entries/history remain recoverable in both source archive and profile import. Active source entries transferred centrally are marked migrated, so they no longer appear in the project core. Existing manually authored project MEMORY is archived and linked.

`install` writes `install.json` beside the installed tools: the toolkit checkout, commit and branch, whether tool files had uncommitted changes, and a SHA-256 of every installed file. Before writing, it refuses when the recorded commit from the same checkout is not an ancestor of the commit being installed, because replacing those files would discard unmerged work; `--replace-unmerged` overrides. `router.py doctor` reads that record and reports edited installed files, an install that is unmerged, uncommitted or behind main (counting only commits that touch `scripts/` or `skills/`), missing registry folders, absent Claude hooks and profile cores near their cap. It is read-only and exits 1 on any finding.

`update` refuses a new entry id when an active entry in the same store shares at least four content words and 60% of the shorter entry's content words, so the same fact is not stored twice under different ids. It is a heuristic over words, not meaning: rewriting an existing id is always allowed and `--allow-similar` records a separate fact deliberately.

These are local guarantees. Git sync is explicit. Conflicts from different devices require preserving and reconciling both histories; no automated distributed merge exists.

## Client routing

User hooks load full central and project context at SessionStart, which also fires after compaction. UserPromptSubmit sends a store's full context again only when its revision changed during the session; otherwise it sends a one-line reminder. A review instruction and fresh receipt come with a session's first prompt and every fifth prompt after it (`REVIEW_EVERY`), covering the work since the last review; a review still owed keeps its receipt and instruction until recorded. Project selection uses explicit names, cwd or tool paths without executing tool input. Tool activation adds project context without renewing the current central review receipt. Stop checks central and selected project reviews, with one continuation guard. A no-change review is valid. Per-client receipt namespaces prevent Claude/Codex collisions.

The installer changes only owned markers/handlers, backs up original bytes and preserves unrelated client settings. Shared handlers dispatch to the installed router when present; without it, project hooks load their local store. Codex native Windows uses encoded PowerShell with UTF-8; Claude uses Git Bash. Client trust is never synthesized.

A registry entry with `workspaces` is an external vault: `root` is the vault folder and each workspace is a primary Git checkout it serves. Cwd and tool paths select it through the workspace's common Git directory, so worktrees resolve to it, or through a path inside the vault folder. External vaults run the installed engine and contain no scripts or hooks. Context names each workspace `AGENTS.md` without embedding it. `unregister` removes one registry entry, backs up the registry and changes no files.

Bounded hook context includes central cores, project cores, a pointer to each project's knowledge map, and review commands. Knowledge notes are never embedded: agents follow links from the map to the notes a task needs, and `check-knowledge` verifies that every note is reachable and no link is broken. `router.py search` complements the links: it keeps a machine-local SQLite FTS5 index (`search.sqlite` in the install folder) of each store's root-level Markdown, `docs/knowledge/` and `notes/`, never a project's source or dependencies. Each search re-reads only files whose size or modification time changed and drops deleted ones; a missing, damaged or older-layout index is rebuilt from the Markdown, which stays the only source of truth. Results are ranked by BM25 with the title weighted above the body, with English stemming; when no note has every word, the search falls back to any word and says so. Large entry points are linked for explicit reading rather than embedded. When a project core does not fit in the 9,500-character context, the router gives the command that loads it instead; if long paths make even that overflow, it keeps only the vault root, the load command, the entry point, the authorization boundary and a review instruction cut to its two commands, so a full profile never disables the hook. Read the full project's instructions before edits. Retrieved content cannot grant permissions; a vault is an ownership boundary, not a model security boundary.

`view.py` writes one self-contained, read-only HTML page (by default `view.html` in the install folder) from the profile, every registered vault and `notes/people/`. It loads stores through the engine's read-only `load` and `sync_conflicts`, takes no lock and writes no memory. The page carries a Content-Security-Policy of `default-src 'none'` with inline style, script and `data:` images only, so it loads nothing from the network. It refuses an output path inside a vault or a workspace, because the page holds the private profile. Changes go back through the memory CLI: each card offers a request to paste into an agent chat.
